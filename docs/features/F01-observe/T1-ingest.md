# T1: Ingest API + Postgres

**Цель:** сервер принимает нативный payload http-хука Claude Code и идемпотентно пишет его в Postgres.

**Статус:** выполнен

## Кто что пишет
- Агент (рутина): `docker-compose.yml` с Postgres, `go mod init`, скелет `backend/cmd/server`, Makefile, sqlc/migrate-golang конфиги, `oapi-codegen` и `make generate`.
- Владелец (ядро): миграции, SQL-запросы, адаптер `claudecode`, реализация сгенерированного `StrictServerInterface` (метод `IngestClaudeHook`), middleware токена, тесты.
- Фактически: по просьбе владельца («не смогу написать и понять») агент написал SQL-запросы, тесты, `ingest.Service`, адаптер, `httpapi` и `main.go`, а также дописал миграцию `events`. Миграцию `runs` писал владелец, агент только ревьюил. Владелец ревьюит и дальше правит сам.

## Что сделать
1. Миграции goose для `runs` и `events` (см. feature.md).
2. Эндпоинт `POST /hooks/claude`:
   - проверка токена из заголовка `Authorization: Bearer` (`crypto/subtle`), иначе 401;
   - адаптер `claudecode`: JSON хука → внутренняя структура события;
   - лимит тела 10 МиБ (`http.MaxBytesReader`), сверх лимита `413`;
   - upsert `runs` по `session_id`: любое событие новой сессии создаёт Run (`started_at` = время получения первого события), любое последующее событие заново открывает существующий (`running`, `finished_at = NULL`; изменено в T2: `SessionStart` по http не приходит, см. `docs/notes/hooks-reality.md`), закрывает только `SessionEnd`; `Stop` это обычное событие;
   - `task_text` заполняется из первого `UserPromptSubmit`;
   - вставка события с `ON CONFLICT DO NOTHING` по частичному ключу идемпотентности (только события с `tool_use_id`), остальные пишутся всегда; `seq` назначается в БД внутри транзакции;
   - ответ быстро, `200` с пустым телом (хук не ждёт).
3. Неизвестный `hook_event_name` сохраняется как есть, без ошибки.

## Критерии приёмки
- Повторная отправка того же `PreToolUse`/`PostToolUse` не создаёт второго события.
- Два `Stop` в одной сессии дают два события.
- `SessionEnd` закрывает Run, любое следующее событие открывает его снова (изменено в T2).
- Два параллельных запроса на один `run` дают разные `seq` без дублей.
- Тесты на реальном Postgres (testcontainers): идемпотентность и параллельность, тест сначала.
- Без токена 401.

## Принятые решения
- Путь эндпоинта `POST /api/v1/hooks/claude`: префикс из `servers.url` спеки. URL в хуках T2 должен его включать.
- `seq` без счётчика в `runs`: `UpsertRun` (`ON CONFLICT DO UPDATE`) блокирует строку Run до конца транзакции, затем `MAX(seq)+1` внутри `InsertEvent`. Запасной `UNIQUE (run_id, seq)`. Тест на параллельность ловит поломку этой схемы.
- Транзакция одна на событие: `UpsertRun` → `SetRunTaskText` или `FinishRun` → `InsertEvent`.
- Run открывает любое событие, в том числе `Stop` после `SessionEnd` (изменено в T2, было: только `SessionStart`). Компромисс: запоздавшее событие после `SessionEnd` переоткроет Run.
- Если `cwd` не пришёл, `runs.cwd` = `''`, он дополняется, когда придёт в следующем событии (закрывает вопрос T0).
- Пустой `tool_use_id` считается отсутствующим (`NULL`), такое событие пишется всегда.
- В `events.payload` лежит исходное тело хука без изменений. Для этого `limitBody` кладёт сырые байты в контекст, сгенерированный декодер их бы потерял.
- Токен сравнивается через `crypto/subtle` по SHA-256 хэшам (длина токена не утекает). Проверка на всём `/api/v1/`, `/healthz` без токена.
- Ошибки разбора тела и параметров идут в формате `ErrorResponse` (закрывает вопрос T0). Ошибки хранилища: 500 с общим текстом, детали в логе.
- Эндпоинты чтения (`ListRuns`, `GetRun`, `ListRunEvents`) пока отвечают 500 `not implemented`, их делает T3.
- Первичный ключ `events` это `(id, ts)`; уникальные индексы без `ts` придётся пересобрать при партиционировании.
- Локально Postgres в Docker вынесен на порт `5433` (`.env`, не в git): на `5432` был посторонний Postgres.
